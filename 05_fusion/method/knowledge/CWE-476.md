# CWE-476: NULL Pointer Dereference

## 1. Weakness Characteristics

The core issue is that code dereferences a pointer or pointer-like handle on a path where it can still be null.

---

## 2. Expected Secure Behavior

A dereference should occur only after the pointer's non-null validity is established and preserved until the access happens.

---

## 3. Evidence Supporting TP

- Evidence: A value that can legally be null reaches a dereference without an effective prior guard.
  Explanation: The warning is supported when null remains feasible at the exact use site.
- Evidence: A function that may return null has its result dereferenced without checking success or fallback state.
  Explanation: Ignoring nullable-return semantics creates a direct defect path.
- Evidence: A null check exists but is on a different path, after the dereference, or for a different alias.
  Explanation: Superficial checking does not prove safety for the reported use.
- Evidence: Concurrency, invalidation, or callback sequencing can make a previously checked pointer null again before use.
  Explanation: Non-null must hold at dereference time, not only earlier in the function.

---

## 4. Evidence Supporting FP

- Evidence: A dominating runtime condition, explicit runtime validation, or constructor invariant proves the pointer is non-null on every path to the dereference.
  Explanation: If null is impossible at the use site, the warning does not indicate a real defect.
- Evidence: The apparent dereference target is handled safely by the called API even when the argument is null.
  Explanation: Some APIs accept null and implement fallback behavior, so the reported operation is not an unsafe dereference.
- Evidence: The warning follows an alias that appears nullable locally, but the actual alias used at dereference has already been validated or normalized.
  Explanation: Alias confusion can make a safe path look unsafe.
- Evidence: The null-producing path exits, returns, throws, or otherwise cannot flow into the reported dereference.
  Explanation: Path infeasibility is a direct reason to reject the warning.

---

## 5. Important Analysis Questions

1. Question: Can the pointer actually be null at the reported dereference site?
   Why it matters: Nullability at declaration or return site is not enough; it must survive to the use site.
2. Question: Which guards dominate the dereference, and do they protect the same alias?
   Why it matters: A check only matters if it applies to the exact value being used.
3. Question: What are the API semantics of the function that produced or consumed the pointer?
   Why it matters: Nullable return values and null-tolerant callees change the meaning of the warning.
4. Question: Can the pointer be invalidated, reset, or swapped after a prior check?
   Why it matters: Earlier validation may not hold across later control-flow steps.
5. Question: Are project invariants guaranteeing object existence at this program point?
   Why it matters: Some code omits explicit checks because the surrounding framework enforces non-null state.

---

## 6. Common Misleading Patterns

- later null check that does not protect the earlier dereference
- checking one alias and dereferencing another
- null-tolerant APIs misread as unsafe dereferences
- framework or parser invariants that guarantee non-null objects
- prior check invalidated by later reassignment or callback effects

---

## 7. Required Context for Reliable Judgment

- pointer origin and nullability contract
- exact dereference site and alias identity
- dominating guards and exits
- callee semantics for null handling
- project invariants and lifecycle rules

---

## 8. Static Analysis Warning Validation Notes

This specification is intended to assist static analysis warning validation.
The CWE category alone does not determine whether a warning is a real defect.
The final judgment should be based on the reported warning location, code path, data flow, control flow, API semantics, and project-specific behavior.
