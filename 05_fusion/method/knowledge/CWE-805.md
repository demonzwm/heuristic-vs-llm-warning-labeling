# CWE-805: Buffer Access with Incorrect Length Value

## 1. Weakness Characteristics

The core issue is that a buffer read or write uses a length value that does not match the true accessible extent of the buffer from the current position.

---

## 2. Expected Secure Behavior

Length arguments should represent the exact safe access span for the actual buffer and current offset used by the operation.

---

## 3. Evidence Supporting TP

- Evidence: A length parameter is larger than the destination capacity or readable source extent from the reported position.
  Explanation: The warning is supported when the operation trusts an incorrect length and therefore accesses outside bounds.
- Evidence: The length is derived from unrelated metadata, total object size, or source-controlled values instead of the actual remaining span.
  Explanation: Mismatched length provenance is a strong sign that the operation can exceed the valid region.
- Evidence: Pointer advancement occurs before the operation, but the original length is reused without subtracting consumed bytes.
  Explanation: A once-correct length can become wrong after offsetting into the buffer.
- Evidence: Signedness, truncation, element-versus-byte confusion, or overflow changes the intended length before the access.
  Explanation: Numeric misinterpretation can silently inflate or corrupt the effective access width.

---

## 4. Evidence Supporting FP

- Evidence: The supplied length is conservative relative to the actual remaining accessible region.
  Explanation: An unusual length expression is not a defect if it still upper-bounds the access safely.
- Evidence: The callee interprets the length differently than the warning assumes, and that interpretation keeps the access within bounds.
  Explanation: API-specific length semantics are a common source of false positives.
- Evidence: The length is normalized, clamped, or rejected by an earlier helper before the reported operation executes.
  Explanation: Local code may look unsafe while upstream logic already enforces the correct bound.
- Evidence: The visible buffer is a slice of a larger contiguous region and the length remains valid for that larger storage.
  Explanation: Partial object modeling can make a correct length appear wrong.

---

## 5. Important Analysis Questions

1. Question: What does the length value mean for this API: bytes to copy, source limit, destination capacity, or remaining space?
   Why it matters: Correct judgment depends on the callee's interpretation of the argument.
2. Question: Is the length tied to the actual buffer being accessed, or to a different object or earlier state?
   Why it matters: Wrong provenance often explains both true defects and misleading warnings.
3. Question: Has the pointer moved since the length was computed?
   Why it matters: Remaining span after offset is frequently smaller than the stored length.
4. Question: Are there unit conversions, signedness changes, or overflow risks in the length derivation chain?
   Why it matters: Length bugs often come from numeric transformation rather than obviously missing checks.
5. Question: Does any helper clamp, reinterpret, or validate the supplied length before access?
   Why it matters: API and wrapper semantics can neutralize an otherwise suspicious length value.

---

## 6. Common Misleading Patterns

- total length reused after pointer advancement
- confusing destination capacity with copy count
- source-size checks treated as destination-size checks
- wrapper functions that clamp lengths internally
- bytes versus elements confusion

---

## 7. Required Context for Reliable Judgment

- exact API contract for the length argument
- length derivation and numeric transformations
- current pointer offset and remaining span
- source and destination object extents
- wrapper/helper validation behavior

---

## 8. Static Analysis Warning Validation Notes

This specification is intended to assist static analysis warning validation.
The CWE category alone does not determine whether a warning is a real defect.
The final judgment should be based on the reported warning location, code path, data flow, control flow, API semantics, and project-specific behavior.
