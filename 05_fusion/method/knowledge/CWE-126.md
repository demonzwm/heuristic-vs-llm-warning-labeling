# CWE-126: Buffer Over-read

## 1. Weakness Characteristics

The core issue is a sequential or width-based read that continues past the available buffer because the consumed length is too large for the actual readable region.

---

## 2. Expected Secure Behavior

Sequential parsing, scanning, copying, or decoding should stop within the actual buffer extent and should not rely on unproven length, sentinel, or structure assumptions.

---

## 3. Evidence Supporting TP

- Evidence: A loop, parser, or copy reads until a count, delimiter, or format condition that is not guaranteed to occur within the buffer.
  Explanation: Sequential logic can over-read even when each individual step seems small.
- Evidence: The code reads a fixed-width structure, chunk, or vector from a position near the end of the buffer without checking remaining bytes.
  Explanation: Valid starting positions do not make a full-width read safe.
- Evidence: The claimed readable length comes from metadata that can disagree with the actual backing storage.
  Explanation: Over-read becomes feasible when the code trusts a larger logical length than the physical buffer.
- Evidence: The read path combines offset plus length without guarding against the total consumed range.
  Explanation: Range safety must cover the whole span, not only one endpoint.

---

## 4. Evidence Supporting FP

- Evidence: A dominating check proves the remaining bytes are at least the full sequential or fixed-width read length.
  Explanation: When the consumed span is validated before read, the warning does not indicate a real over-read path.
- Evidence: The buffer is guaranteed to contain required sentinels, padding, or trailing bytes by producer-side invariants.
  Explanation: Apparent over-read risk can disappear when object layout guarantees the parser's assumptions.
- Evidence: The read helper stops early, clamps length, or returns failure before dereferencing beyond the valid region.
  Explanation: The tool may flag the caller while the callee already enforces safe termination.
- Evidence: The reported buffer view is smaller than the actual contiguous readable storage used by the implementation.
  Explanation: Modeling only the visible slice can make a legal sequential read look unsafe.

---

## 5. Important Analysis Questions

1. Question: How many bytes or elements can the operation consume on the reported path?
   Why it matters: Buffer over-read depends on total consumption, not just the first dereference.
2. Question: Is remaining capacity checked from the current offset, not from the buffer start?
   Why it matters: Sequential consumers frequently start from interior positions.
3. Question: Are delimiters, sentinels, padding, or framing bytes guaranteed to exist?
   Why it matters: Many false positives and true positives turn on hidden layout assumptions.
4. Question: Does the parser read multi-byte fields, vectors, or structures in one step?
   Why it matters: Wider reads need stronger remaining-length proofs.
5. Question: Which component owns the authoritative length: caller, callee, metadata, or allocation?
   Why it matters: Mismatched authorities are a common source of real over-reads.

---

## 6. Common Misleading Patterns

- checking a total length but not remaining bytes after offset
- assuming delimiter presence without proving construction invariants
- helper functions that fail closed before over-reading
- fixed-width reads near buffer tail
- analyzer confusion between visible slice length and real backing storage

---

## 7. Required Context for Reliable Judgment

- current offset and remaining readable bytes
- total consumed width of the operation
- layout guarantees such as padding or terminators
- parser/helper failure behavior
- source of truth for length metadata

---

## 8. Static Analysis Warning Validation Notes

This specification is intended to assist static analysis warning validation.
The CWE category alone does not determine whether a warning is a real defect.
The final judgment should be based on the reported warning location, code path, data flow, control flow, API semantics, and project-specific behavior.
