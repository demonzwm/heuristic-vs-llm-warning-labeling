# CWE-119: Improper Restriction of Operations within the Bounds of a Memory Buffer

## 1. Weakness Characteristics

The core issue is that code performs a read, write, copy, or pointer movement without a reliable guarantee that the accessed region stays within the intended buffer bounds.

---

## 2. Expected Secure Behavior

Every buffer operation should be constrained by bounds that are valid for the exact object being accessed, for the exact offset and length used on the executed path.

---

## 3. Evidence Supporting TP

- Evidence: A computed pointer or index can move outside the allocated object before the reported access.
  Explanation: The warning reflects a real defect when the dangerous address calculation is feasible on an executed path.
- Evidence: The access size depends on external input, propagated length fields, or arithmetic that is not checked against the actual buffer extent.
  Explanation: Untrusted or stale size information can make an apparently normal memory operation exceed the intended region.
- Evidence: A guard exists, but it is applied after the first access or does not constrain the same offset, index, or length that the warning reports.
  Explanation: A late or mismatched check does not make the reported operation safe.
- Evidence: The code assumes two buffers have compatible sizes, but no contract, allocation proof, or normalization step establishes that relationship.
  Explanation: Without a proven size relation, cross-buffer operations can violate bounds even if each buffer is valid on its own.

---

## 4. Evidence Supporting FP

- Evidence: The reported access is dominated by a guard that proves both the starting position and the full access range stay inside the same object.
  Explanation: If the guard is effective on all incoming paths, the warning does not describe a reachable out-of-bounds operation.
- Evidence: Buffer size and offset are derived from constants, validated metadata, or a checked helper that already enforces the required invariant.
  Explanation: The tool may miss project-specific normalization that makes the access safe.
- Evidence: The apparent buffer is a flexible layout, segmented object, or larger enclosing allocation, and the reported access remains inside the true storage extent.
  Explanation: A warning can be misleading when it reasons about a subobject while the implementation intentionally accesses a larger backing region.
- Evidence: The API being called clamps the effective access length or rejects invalid ranges internally.
  Explanation: The dangerous-looking call site may be safe because the callee enforces the real boundary.

---

## 5. Important Analysis Questions

1. Question: Can the reported access path actually execute with the shown offset and length values?
   Why it matters: An infeasible path does not support a real buffer-bound violation.
2. Question: What is the exact allocated extent of the accessed object on this path?
   Why it matters: Safety depends on the real object size, not only on local variable names or declared element counts.
3. Question: Do the checks constrain the same pointer, index, base object, and access width as the warning?
   Why it matters: Related-looking checks may protect a different quantity.
4. Question: Are offset and length values transformed before use by casts, scaling, subtraction, truncation, or sentinel logic?
   Why it matters: Bound errors often arise after arithmetic changes the meaning of the checked value.
5. Question: Does any called helper enforce clamping, validation, or early failure?
   Why it matters: API semantics can convert an apparent risk into a safe operation.

---

## 6. Common Misleading Patterns

- a later bounds check does not protect an earlier access
- checking element count but not scaled byte count
- validating one buffer while accessing another
- reasoning on declared array size when the true storage is larger or dynamic
- helper functions that silently clamp ranges

---

## 7. Required Context for Reliable Judgment

- exact access expression and width
- allocation or object-layout context
- offset/length derivation chain
- dominating guards and early exits
- callee implementation or API contract

---

## 8. Static Analysis Warning Validation Notes

This specification is intended to assist static analysis warning validation.
The CWE category alone does not determine whether a warning is a real defect.
The final judgment should be based on the reported warning location, code path, data flow, control flow, API semantics, and project-specific behavior.
