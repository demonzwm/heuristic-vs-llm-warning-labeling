# CWE-131: Incorrect Calculation of Buffer Size

## 1. Weakness Characteristics

The core issue is an allocation or capacity computation that produces the wrong size, causing later accesses to operate on a buffer smaller than the code assumes.

---

## 2. Expected Secure Behavior

Buffer size calculations should match the real number of bytes required for payload, element width, metadata, alignment, and any terminator or sentinel needed by later accesses.

---

## 3. Evidence Supporting TP

- Evidence: Allocation size is derived from arithmetic that omits element width, terminator space, separators, headers, or alignment.
  Explanation: A later access can be unsafe even if the access itself uses a bounded API, because the buffer was undersized from the start.
- Evidence: Size math can overflow, truncate, sign-convert, or otherwise lose information before allocation.
  Explanation: The computed capacity may be smaller than intended while appearing syntactically valid.
- Evidence: The code allocates based on one interpretation of length but accesses based on another, such as bytes versus elements.
  Explanation: Unit mismatch creates a real discrepancy between provisioned and consumed space.
- Evidence: A conditional or macro-based size expression chooses the wrong branch or precedence, yielding too small a buffer.
  Explanation: Subtle expression errors can systematically under-allocate.

---

## 4. Evidence Supporting FP

- Evidence: The reported calculation is conservative but still produces a buffer at least as large as the maximum later access.
  Explanation: An unusual formula is not a defect if it still establishes a safe lower bound.
- Evidence: Additional space is provided elsewhere through padding, enclosing allocation, or allocator semantics visible in context.
  Explanation: The apparent local calculation may not define the full usable storage.
- Evidence: The suspicious arithmetic occurs on an unreachable path or is followed by a fail-closed check before any use.
  Explanation: Incorrect-looking size math does not matter if the undersized buffer is never used unsafely.
- Evidence: The code intentionally allocates for a truncated representation and all later writes/reads honor that smaller contract.
  Explanation: Smaller allocation is only a defect when later behavior exceeds the chosen representation.

---

## 5. Important Analysis Questions

1. Question: What exact later accesses rely on this computed size?
   Why it matters: A size-calculation warning is only actionable when it affects real subsequent operations.
2. Question: Are units consistent across calculation, allocation, and use?
   Why it matters: Bytes, elements, and encoded lengths are often mixed incorrectly.
3. Question: Is terminator, sentinel, framing, or alignment space required?
   Why it matters: Many near-correct allocations fail because required overhead was omitted.
4. Question: Can the arithmetic overflow, truncate, or change sign before allocation?
   Why it matters: Correct formulas can still become wrong after numeric conversion.
5. Question: Does the actual allocation include extra capacity beyond the visible expression?
   Why it matters: Full context may show that the real buffer is larger than the local calculation suggests.

---

## 6. Common Misleading Patterns

- byte count versus element count confusion
- forgetting space for a terminator while later code appends one
- arithmetic precedence mistakes
- allocator wrappers that add hidden slack or metadata
- suspicious math on paths that never reach use sites

---

## 7. Required Context for Reliable Judgment

- full allocation expression and involved types
- later accesses that consume the buffer
- unit conventions used by the project
- overflow/truncation behavior of the numeric types
- allocator or wrapper semantics

---

## 8. Static Analysis Warning Validation Notes

This specification is intended to assist static analysis warning validation.
The CWE category alone does not determine whether a warning is a real defect.
The final judgment should be based on the reported warning location, code path, data flow, control flow, API semantics, and project-specific behavior.
