# CWE-125: Out-of-bounds Read

## 1. Weakness Characteristics

The core issue is that code can read memory outside the intended object bounds through an invalid index, pointer, offset, or derived length.

---

## 2. Expected Secure Behavior

A read should only occur when both the starting address and the full consumed range are proven to stay within the valid readable extent of the target object.

---

## 3. Evidence Supporting TP

- Evidence: The code reads using an index or pointer that can exceed the last valid element on a feasible path.
  Explanation: A reachable invalid position directly supports a real out-of-bounds read.
- Evidence: Bounds are checked only after the first dereference or after advancing the pointer.
  Explanation: A late check does not retroactively protect an earlier read.
- Evidence: The read depends on sentinel termination, length metadata, or loop conditions that are not guaranteed to match the actual object extent.
  Explanation: The code may continue reading past the buffer when the assumed stopping condition fails.
- Evidence: Arithmetic, sign conversion, or underflow can create a negative or oversized effective offset before the read.
  Explanation: The dangerous address can be produced even if the original variable looked constrained.

---

## 4. Evidence Supporting FP

- Evidence: A dominating guard proves the reported read occurs only when index and width stay within the valid range.
  Explanation: The warning is weakened when reachability and read width are both bounded before access.
- Evidence: The object is guaranteed to contain a sentinel, fixed trailer, or validated extent by protocol or project invariant.
  Explanation: Some reads that look unconstrained are safe because object construction guarantees the stopping condition.
- Evidence: The reported access is within a larger enclosing allocation, packed object, or legal one-past navigation that is not actually dereferenced unsafely.
  Explanation: Analyzer reasoning may be too narrow about the true readable region.
- Evidence: A helper already validated the range or normalized the offset before the current function uses it.
  Explanation: The local code may appear unsafe while the precondition is already enforced upstream.

---

## 5. Important Analysis Questions

1. Question: Can the reported read location be reached with the suspicious index or offset?
   Why it matters: A warning is only meaningful when the bad state is feasible.
2. Question: What exact object is being read, and what is its true readable extent?
   Why it matters: Correct judgment depends on the actual storage region, not only on local declarations.
3. Question: Does the code read before checking, or does it check the same value before every read step?
   Why it matters: Order of evaluation often determines whether the warning is real.
4. Question: Are sentinel, terminator, or metadata assumptions guaranteed by construction?
   Why it matters: Read safety often depends on hidden object-creation guarantees.
5. Question: Is the access width larger than one element, such as structured parsing or multi-byte decoding?
   Why it matters: A valid starting index may still permit an out-of-bounds read of the full width.

---

## 6. Common Misleading Patterns

- range check placed after the dereference
- validating element index but not multi-byte read width
- safe protocol invariants not visible to the analyzer
- one-past pointer arithmetic mistaken for an immediate invalid read
- helper normalization performed earlier in the call chain

---

## 7. Required Context for Reliable Judgment

- object extent and layout
- index/offset derivation chain
- read width and loop semantics
- ordering between checks and reads
- upstream validation or construction invariants

---

## 8. Static Analysis Warning Validation Notes

This specification is intended to assist static analysis warning validation.
The CWE category alone does not determine whether a warning is a real defect.
The final judgment should be based on the reported warning location, code path, data flow, control flow, API semantics, and project-specific behavior.
