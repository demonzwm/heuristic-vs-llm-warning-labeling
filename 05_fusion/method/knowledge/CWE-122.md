# CWE-122: Heap-based Buffer Overflow

## 1. Weakness Characteristics

The core issue is a write that can exceed the bounds of heap-allocated storage because allocation size, remaining capacity, offset, or write length is not correctly enforced.

---

## 2. Expected Secure Behavior

Writes to heap memory should use the true allocated size of the target object and should only proceed when the full write range is proven to stay inside that allocation.

---

## 3. Evidence Supporting TP

- Evidence: Heap memory is allocated with a size that is too small for the later write pattern.
  Explanation: A later write can be unsafe even if the write itself looks bounded, because the allocation is already undersized.
- Evidence: The write length comes from parsed metadata, input length, or arithmetic that is not checked against the actual allocation.
  Explanation: Heap safety depends on the real allocated extent, not on assumed protocol values.
- Evidence: Reallocation, growth, or ownership changes can leave a stale capacity variable that the write still trusts.
  Explanation: The warning is supported when the tracked size no longer matches the live heap object.
- Evidence: Pointer arithmetic advances into the heap object and the remaining capacity is not recomputed before write.
  Explanation: Using total capacity instead of remaining capacity can make an otherwise bounded API overflow.

---

## 4. Evidence Supporting FP

- Evidence: Allocation size and write size are linked by a dominating invariant that proves sufficient heap capacity.
  Explanation: If the live object size is correctly propagated to the write site, the warning may be spurious.
- Evidence: The object is heap-backed but managed by a container or builder that expands or clamps internally before writing.
  Explanation: The analyzer may miss dynamic-capacity management performed by the abstraction.
- Evidence: The suspicious pointer targets a larger shared allocation or arena slice whose valid range exceeds the local field size.
  Explanation: Incomplete modeling of heap layout can make a safe write look out of bounds.
- Evidence: A failed resize or allocation path exits before the reported write is reachable.
  Explanation: The dangerous write is not a real defect if the bad state cannot survive control-flow checks.

---

## 5. Important Analysis Questions

1. Question: What is the exact allocated size of the heap object at the moment of the reported write?
   Why it matters: Heap objects can change size or identity over time.
2. Question: Was the buffer resized, reallocated, or replaced earlier on this path?
   Why it matters: Capacity reasoning is often invalidated by heap-management steps.
3. Question: Is the size variable used by the write still synchronized with the live allocation?
   Why it matters: Stale capacity metadata is a frequent source of real defects and false alarms.
4. Question: Does the destination pointer start at the object base or at an interior offset?
   Why it matters: Remaining capacity may differ substantially from total allocation size.
5. Question: Does a helper abstraction grow, clamp, or reject oversized writes?
   Why it matters: Container and builder semantics can decide whether the warning is real.

---

## 6. Common Misleading Patterns

- using total allocation size after pointer advancement
- trusting stale length/capacity fields after realloc or ownership transfer
- larger backing allocations hidden behind smaller local views
- early error paths that make the bad write unreachable
- container abstractions that resize internally

---

## 7. Required Context for Reliable Judgment

- allocation and reallocation history
- live capacity metadata
- pointer offsets into the heap object
- error handling and early-return paths
- abstraction semantics for dynamic buffers

---

## 8. Static Analysis Warning Validation Notes

This specification is intended to assist static analysis warning validation.
The CWE category alone does not determine whether a warning is a real defect.
The final judgment should be based on the reported warning location, code path, data flow, control flow, API semantics, and project-specific behavior.
