# CWE-676: Use of Potentially Dangerous Function

## 1. Weakness Characteristics

The core issue is not the function name alone, but whether the call relies on preconditions that are strong enough to make a dangerous-capability API safe in this specific context.

---

## 2. Expected Secure Behavior

Potentially dangerous functions should only be called when their memory, length, lifetime, format, and input assumptions are explicitly satisfied on the executed path.

---

## 3. Evidence Supporting TP

- Evidence: The call uses a function whose behavior can violate safety unless the caller proves size, termination, format, or aliasing preconditions, and that proof is missing.
  Explanation: The warning is supported when the API exposes dangerous capability and the call site does not establish the required safety conditions.
- Evidence: Safer wrappers, bounded variants, or project-mandated checks are bypassed.
  Explanation: Direct use of the dangerous API becomes meaningful when established safety discipline is skipped.
- Evidence: Arguments come from uncontrolled or weakly validated data and directly drive the risky behavior of the function.
  Explanation: Dangerous APIs amplify unchecked inputs into concrete defect paths.
- Evidence: The call appears in a context already associated with lifetime, bounds, or format uncertainty.
  Explanation: When surrounding semantics are unstable, using a risky primitive strengthens the case for a real defect.

---

## 4. Evidence Supporting FP

- Evidence: The caller establishes all relevant preconditions before the function is used.
  Explanation: A dangerous function can still be safe when the exact call context satisfies its contract.
- Evidence: Project wrappers, macros, or platform substitutes redefine the function with safer semantics.
  Explanation: Warning logic based only on the function name may not match the actual implementation used in the build.
- Evidence: The function is used on fixed-size, compile-time-known data with a proven bound relation.
  Explanation: Some calls are safe because the risky behavior is not reachable with the actual arguments.
- Evidence: The warning is purely name-based and no unsafe path, length issue, or format issue can be demonstrated in the provided code.
  Explanation: Function choice alone is insufficient evidence of a real defect.

---

## 5. Important Analysis Questions

1. Question: What exact safety preconditions does this function require from its caller?
   Why it matters: Correct judgment depends on the actual contract, not on the reputation of the API.
2. Question: Are those preconditions established on every path that reaches the call?
   Why it matters: One unprotected path is enough for a real defect.
3. Question: Is the called symbol the standard dangerous implementation, a wrapper, or a safer replacement?
   Why it matters: Build-time or project-level indirection can change semantics.
4. Question: What argument controls the dangerous behavior: length, format string, destination pointer, or lifetime-sensitive object?
   Why it matters: The relevant evidence depends on how the function can become unsafe.
5. Question: Does the codebase have conventions that restrict use of this function to provably safe contexts?
   Why it matters: Project discipline may explain why an otherwise suspicious call is safe.

---

## 6. Common Misleading Patterns

- name-based warnings without path-specific unsafe evidence
- wrapper or macro redefinitions that change semantics
- fixed-size safe calls to traditionally risky APIs
- safer project conventions enforced outside the local snippet
- dangerous-function warnings that actually depend on another CWE such as bounds or nullability

---

## 7. Required Context for Reliable Judgment

- true callee implementation or wrapper mapping
- caller-established preconditions
- argument provenance and constraints
- project coding conventions for risky APIs
- nearby evidence of bounds, lifetime, or format safety

---

## 8. Static Analysis Warning Validation Notes

This specification is intended to assist static analysis warning validation.
The CWE category alone does not determine whether a warning is a real defect.
The final judgment should be based on the reported warning location, code path, data flow, control flow, API semantics, and project-specific behavior.
