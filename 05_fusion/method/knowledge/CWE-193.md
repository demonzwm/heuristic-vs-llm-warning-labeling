# CWE-193: Off-by-one Error

## 1. Weakness Characteristics

The core issue is a boundary miscalculation by one unit, often at the first invalid element, the final valid element, or the space reserved for a terminator.

---

## 2. Expected Secure Behavior

Boundary logic should distinguish clearly between element count, last valid index, and total required capacity, including any final terminator or sentinel write.

---

## 3. Evidence Supporting TP

- Evidence: Loop or copy logic allows index `== size` when the valid last index is `size - 1`.
  Explanation: A single extra iteration or write can make the warning a real defect even when the rest of the logic is correct.
- Evidence: The code writes a terminator, delimiter, or sentinel after filling all nominal payload slots.
  Explanation: Reserve-space mistakes commonly turn a nearly safe operation into an out-of-bounds write.
- Evidence: Boundary checks use `<` versus `<=` inconsistently across related accesses.
  Explanation: Inconsistent comparisons can make one specific boundary value unsafe.
- Evidence: Pointer-end calculations treat one-past positions as readable or writable rather than only comparable.
  Explanation: One-past semantics are limited; dereference or write there supports the warning.

---

## 4. Evidence Supporting FP

- Evidence: The data structure intentionally includes an extra slot, pad byte, or terminator space, and the reported boundary value remains inside that design.
  Explanation: Apparent off-by-one behavior may be safe when the allocated contract already accounts for it.
- Evidence: The reported comparison value is exclusive and the access occurs only before the exclusive end.
  Explanation: Tools often misread half-open interval logic as a boundary defect.
- Evidence: The suspicious index is computed but not used for an actual read or write on the flagged path.
  Explanation: A boundary expression alone is not enough without a corresponding unsafe access.
- Evidence: The helper API clamps the effective count before the final element or terminator write.
  Explanation: Local fencepost concerns can be neutralized by callee semantics.

---

## 5. Important Analysis Questions

1. Question: Which boundary convention is intended here: closed interval or half-open interval?
   Why it matters: Correctness depends on whether the end value is inclusive or exclusive.
2. Question: Is the reported value used for indexing, copying, allocation, or only comparison?
   Why it matters: Off-by-one warnings need a real effect on memory or logic.
3. Question: Does the code need one extra unit for terminators, sentinels, or separators?
   Why it matters: Many real defects appear only at the final bookkeeping write.
4. Question: Are pointer one-past positions ever dereferenced or written?
   Why it matters: Legal pointer arithmetic becomes unsafe when converted into actual access.
5. Question: Is there any extra capacity or pad element by design?
   Why it matters: Some fencepost-looking cases are safe because the storage contract includes slack.

---

## 6. Common Misleading Patterns

- half-open interval logic mistaken for an inclusive bound bug
- terminator space already reserved but not obvious locally
- computed boundary value that never drives a memory access
- one-past pointer comparison confused with dereference
- loop conditions that look symmetric but protect different actions

---

## 7. Required Context for Reliable Judgment

- exact comparison operators
- which value is used for actual access
- allocation size versus logical payload size
- terminator/sentinel requirements
- pointer arithmetic semantics around end positions

---

## 8. Static Analysis Warning Validation Notes

This specification is intended to assist static analysis warning validation.
The CWE category alone does not determine whether a warning is a real defect.
The final judgment should be based on the reported warning location, code path, data flow, control flow, API semantics, and project-specific behavior.
