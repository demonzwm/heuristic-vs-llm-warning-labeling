# CWE-416: Use After Free

## 1. Weakness Characteristics

The core issue is that code reads from, writes to, or dereferences memory after its lifetime has ended.

---

## 2. Expected Secure Behavior

An object should only be accessed while ownership and lifetime guarantees still hold on the executed path, including across error handling, reference updates, and concurrent interactions if applicable.

---

## 3. Evidence Supporting TP

- Evidence: A pointer is freed, released, or otherwise invalidated before a later reachable access to the same object.
  Explanation: A real use-after-free requires both a lifetime-ending event and a subsequent feasible access.
- Evidence: Aliases to the freed object remain live and are later dereferenced without revalidation.
  Explanation: Nulling one variable or updating one owner does not protect stale aliases.
- Evidence: Error handling, callback sequencing, or ownership transfer can free an object earlier than the later code assumes.
  Explanation: Lifetime bugs often arise from control-flow edges rather than obvious immediate frees.
- Evidence: Reference counting, container removal, or concurrency can drop the last valid ownership before the reported access.
  Explanation: The warning is credible when object lifetime depends on conditions not enforced at the use site.

---

## 4. Evidence Supporting FP

- Evidence: The apparent free only releases a different alias, decrements a non-terminal reference, or marks state without ending lifetime.
  Explanation: Not every release-like call invalidates the accessed object.
- Evidence: A new valid object is assigned to the pointer or alias before the reported access.
  Explanation: Reinitialization can break the supposed free-to-use chain.
- Evidence: Project ownership rules, lifetime-management logic, reference counting, or synchronization semantics explicitly prove the object remains alive until the reported access.
  Explanation: These mechanisms only support rejecting the warning when the actual implementation shows they prevent lifetime invalidation on the reported path.
- Evidence: The reported path requires mutually exclusive branches, impossible sequencing, or a lifetime transition that is ruled out by explicit ownership or synchronization behavior in the implementation.
  Explanation: Concurrency-related reasoning is only useful when the code or documented protocol shows the invalidating sequence cannot occur.

---

## 5. Important Analysis Questions

1. Question: What exact operation ends the object's lifetime on the reported path?
   Why it matters: Reliable judgment requires a real invalidation event, not just a suspicious cleanup call.
2. Question: Is the later access to the same object, or only to a reinitialized or different allocation?
   Why it matters: Alias resolution is central to distinguishing TP from FP.
3. Question: Are there hidden aliases, references, or container entries that still control lifetime?
   Why it matters: Lifetime may persist beyond what one local variable suggests.
4. Question: Can error paths, callbacks, or asynchronous behavior reorder free and use?
   Why it matters: Many true defects live on non-happy-path control flow.
5. Question: What synchronization, ownership, or reference-counting rules does the project enforce?
   Why it matters: Lifetime safety often depends on project-specific conventions.

---

## 6. Common Misleading Patterns

- cleanup-like calls that do not actually free the accessed object
- nulling one alias while others remain live
- reinitialization between release and later use
- reference-count decrements that do not reach zero
- analyzer-reported races that are blocked by locking discipline

---

## 7. Required Context for Reliable Judgment

- object ownership and aliasing
- exact lifetime-ending operations
- control flow from free to use
- reinitialization or replacement steps
- synchronization and reference-count semantics

---

## 8. Static Analysis Warning Validation Notes

This specification is intended to assist static analysis warning validation.
The CWE category alone does not determine whether a warning is a real defect.
The final judgment should be based on the reported warning location, code path, data flow, control flow, API semantics, and project-specific behavior.
