# CWE-120: Buffer Copy without Checking Size of Input ('Classic Buffer Overflow')

## 1. Weakness Characteristics

The core issue is an input-to-output copy or concatenation whose effective copy size can exceed the destination capacity.

---

## 2. Expected Secure Behavior

A copy into a destination buffer should occur only when the destination capacity is known and the effective copied length is proven not to exceed it.

---

## 3. Evidence Supporting TP

- Evidence: Data from a source buffer reaches a copy or append operation without a prior proof that destination capacity is sufficient.
  Explanation: The reported warning is credible when the operation trusts source size or termination without validating the destination.
- Evidence: The code uses an unbounded or conditionally bounded string/memory API while destination size is fixed, smaller, or not established by the visible slice.
  Explanation: The copy length can exceed available space because the operation is not tied to the real destination extent.
- Evidence: The size argument is derived from source-controlled data, stale metadata, or a different object than the actual destination.
  Explanation: A bound that is unrelated to the destination does not prevent overflow.
- Evidence: Null-termination or delimiter assumptions are unchecked before copy/append.
  Explanation: Missing terminators or unexpected lengths can extend the transfer past the intended limit.

---

## 4. Evidence Supporting FP

- Evidence: A dominating check proves destination capacity is at least the exact copied length plus any required terminator.
  Explanation: When the full transfer width is validated before the call, the warning does not describe a real overflow path.
- Evidence: The called API is size-aware and the supplied size corresponds to the true remaining capacity of the destination region.
  Explanation: Some warnings treat any copy as suspicious even when the API contract is safe and correctly used.
- Evidence: The source length is normalized or truncated by a helper before the copy, and that helper's behavior is visible in context.
  Explanation: The effective copied data may already be capped to a safe bound.
- Evidence: The destination is a larger backing allocation, dynamic buffer, or bounded builder object rather than the apparent local subrange.
  Explanation: Apparent local size mismatch may not imply an actual write past the real buffer.

---

## 5. Important Analysis Questions

1. Question: What exact number of bytes or characters can be copied on the reported path?
   Why it matters: The defect depends on effective transfer size, not only on API name.
2. Question: What is the true writable capacity of the destination at the call site?
   Why it matters: Correct judgment requires the actual remaining space, including prior writes and offsetted destinations.
3. Question: Is room for a terminator or delimiter required and accounted for?
   Why it matters: Copy code can be safe for payload bytes but unsafe for the final terminator.
4. Question: Does the callee interpret the size argument as source limit, destination limit, or total buffer size?
   Why it matters: API semantics vary and are a common source of false conclusions.
5. Question: Is the source guaranteed to be terminated, bounded, or length-checked before this operation?
   Why it matters: Source contracts determine how much data the copy may actually consume.

---

## 6. Common Misleading Patterns

- size-aware APIs used with the wrong notion of capacity
- checks that validate source length but ignore destination offset
- wrappers that truncate or reject oversized input before the visible call
- apparent fixed-size arrays that are part of a larger managed buffer
- string copies where terminator handling changes the real write width

---

## 7. Required Context for Reliable Judgment

- destination allocation and remaining capacity
- source length or termination guarantees
- exact API contract for copy/append helpers
- offset into destination before the reported call
- any pre-copy normalization or truncation logic

---

## 8. Static Analysis Warning Validation Notes

This specification is intended to assist static analysis warning validation.
The CWE category alone does not determine whether a warning is a real defect.
The final judgment should be based on the reported warning location, code path, data flow, control flow, API semantics, and project-specific behavior.
