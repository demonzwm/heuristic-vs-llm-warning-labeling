# CWE-121: Stack-based Buffer Overflow

## 1. Weakness Characteristics

The core issue is a write past the bounds of stack-allocated storage such as a local array, stack buffer, or fixed frame object.

---

## 2. Expected Secure Behavior

Writes to stack-resident buffers should stay within the exact local object bounds for all reachable values of index, offset, and copied length.

---

## 3. Evidence Supporting TP

- Evidence: A local fixed-size buffer receives data through indexing, copying, formatting, or concatenation without a proof that the write fits.
  Explanation: Stack objects have rigid bounds, so a feasible oversized write directly supports the warning.
- Evidence: Loop bounds, computed offsets, or format expansion can exceed the local buffer length.
  Explanation: The defect is real when the executed iteration count or expanded output can pass the last valid element.
- Evidence: Stack writes depend on input lengths or decoded fields that are not tightly constrained before use.
  Explanation: Unchecked external sizes can easily exceed a local frame buffer.
- Evidence: The code reserves space incorrectly for separators, sentinels, or a terminator.
  Explanation: Stack overflows often arise from almost-correct size reasoning that misses one extra write.

---

## 4. Evidence Supporting FP

- Evidence: A dominating precondition or loop invariant proves the write range is within the local array extent.
  Explanation: If the proof covers the exact stack object and every write on the path, the warning is not a real overflow.
- Evidence: The buffer is stack-resident but the dangerous-looking operation writes into a bounded subrange whose size is validated.
  Explanation: The tool may overgeneralize from the object type without honoring the local bound proof.
- Evidence: Formatting helpers or builders cap output by the provided local capacity.
  Explanation: A suspicious formatting call can still be safe when the API guarantees truncation or failure.
- Evidence: The apparent local array is only a staging view over a larger object whose actual writable capacity is larger than the visible declaration suggests.
  Explanation: Some warnings arise from incomplete object-layout understanding.

---

## 5. Important Analysis Questions

1. Question: Which exact stack object is reported, and what is its precise capacity?
   Why it matters: Reliable judgment requires the real target object, not just the enclosing function.
2. Question: Can index growth, loop iterations, or format expansion exceed that capacity on any feasible path?
   Why it matters: The warning is valid only if a real write can pass the last valid slot.
3. Question: Is the destination pointer offset into the local buffer before the reported operation?
   Why it matters: Remaining capacity may be smaller than the total array size.
4. Question: Do helper APIs truncate, fail closed, or append a terminator automatically?
   Why it matters: API behavior changes whether the same call is safe or unsafe.
5. Question: Are assertions or debug-only checks the only protection?
   Why it matters: Non-runtime checks may disappear in production and fail to protect the stack write.

---

## 6. Common Misleading Patterns

- checking total array size but ignoring current write offset
- assuming formatted output length equals input length
- debug assertions that are not reliable runtime guards
- wrappers that cap writes even when raw APIs look dangerous
- off-by-one logic around terminators in local arrays

---

## 7. Required Context for Reliable Judgment

- local buffer declaration and effective writable range
- loop and formatting semantics
- destination offsets and remaining space
- compile-mode or assertion behavior if relevant
- helper function contracts for bounded stack writes

---

## 8. Static Analysis Warning Validation Notes

This specification is intended to assist static analysis warning validation.
The CWE category alone does not determine whether a warning is a real defect.
The final judgment should be based on the reported warning location, code path, data flow, control flow, API semantics, and project-specific behavior.
